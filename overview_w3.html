Tonight the last steps are the reports: the pipeline executes its own notebooks, ChartBook turns them into a website, and LaTeX makes the PDF. The habit to build is treating a report not as a document you write once but as a build target the pipeline regenerates whenever the data changes.

Agenda Item 2: Notebooks Are for Reporting#

Last week ended on a point worth repeating. I do not recommend doing your analysis in a notebook. The work belongs in .py files that doit runs as tasks: the pulls, the cleaning, the calculations. A notebook is for reporting. It loads what the tasks produced and presents it, to a coauthor, to a reader, and most often to yourself, with little or no computation of its own.

We pick up where week 2 stopped, in the pydoit/ directory of the in-class examples repo. Example 02 is the same dependency graph on a real project, with a src/ folder and a settings.py. Examples 03 and 04 add notebooks.

Reports with Jupyter Notebooks: why notebooks are for reporting and not for pipeline steps, and how nbconvert executes one from the command line and exports it to HTML. A notebook is then just another doit task, with file dependencies and targets. → HW 1: task_run_notebooks in your dodo.py does exactly this to the six guide notebooks.

How the notebooks here plug into dodo.py. I do not keep a notebook as an .ipynb file. The source of truth is a plain .py file in Jupytext’s percent format, which Git can diff, named so you can tell it is a notebook: 01_markowitz.ipynb.py in HW 0, 02_replicate_GSW2005_ipynb.py in HW 1 and HW 2. VS Code treats each # %% line in the file as a cell and runs it in the Interactive Window, so you still work interactively. The doit task does the rest:

  1. jupytext converts the .py file to .ipynb.

  2. nbconvert executes the notebook and exports it to HTML.

  3. The .ipynb and the HTML land in _output/. They are build artifacts, regenerated from the source and never edited by hand.

The task’s file dependencies are the modules the notebook imports and the files it loads. Change one of those and doit runs the notebook again; otherwise it leaves the rendered copy alone. → HW 2: you add two notebooks to notebook_tasks this way.

Agenda Item 3: ChartBook, the Site as a Build Target#

Say you have several notebooks on Treasury yields, with charts, tables, and commentary, and you want colleagues to browse them as one website. On your own you would set up notebook conversion, a site generator, navigation, and publishing. ChartBook (PyPI) is a small Python package I wrote to take that setup off your hands: it catalogs a project’s notebooks, dataframes, and charts and generates a browsable static site from them.

The workflow, start to finish:

  1. Start a project with chartbook init.

  2. Write the computation in Python modules.

  3. Write the reports as Jupytext notebooks.

  4. Register the outputs worth showing in chartbook.toml.

  5. Generate the static site with chartbook build.

  6. Publish the site with GitHub Pages.

doit and ChartBook do different jobs. doit runs the pipeline and tracks its dependencies. ChartBook does not run your computation: it organizes and publishes what the pipeline produced.

chartbook init builds the new project from a template. Cookiecutter generates a project from a template, as with the Cookiecutter Data Science template you have seen, and Cruft lets a project pull in later updates to the template it came from. The ChartBook project template has the details, and we use it in week 4.

ChartBook also shows where next week is going. It is an ordinary Python package, installed with pip, and you can write one like it: next week we turn your own code into a reusable, installable package.

  • The manifest, chartbook.toml. Each [notebooks.*], [dataframes.*], and [charts.*] entry says what an output is, where it comes from, and where it lives. Read HW 1’s as the example.

  • The CLI and the Python API. chartbook build generates the site; chartbook ls lists what is registered; chartbook data get-path returns a parquet path; and data.load(pipeline=..., dataframe=...) loads it straight into pandas or polars.

  • Where it sits in the pipeline. chartbook build is just another doit task (task_generate_pipeline_site in HW 1), so the site is regenerated whenever the data changes, not assembled by hand. Publishing it is the last item tonight; in week 4, many projects’ manifests aggregate into one catalog.

Agenda Item 4: LaTeX for PDF Reports#

ChartBook is the HTML half of report generation; LaTeX is the PDF half.

LaTeX is code, so a PDF report can be one more target of the pipeline. Python computes the results and writes the figures and tables to files. The .tex file pulls them in with \includegraphics and \input. latexmk compiles the PDF. doit tracks the dependencies, so the report rebuilds when its inputs change.

  • Introduction to LaTeX and LaTeX Essentials: what a .tex file is, how it compiles, and the handful of commands a report needs.

  • Work through the latex/ examples in the in-class repo, a progression from a five-line document through figures and tables, bibliographies, and Beamer slides.

  • Demo: the market brief in latex/08_handout, built from a custom class file, whose charts and returns table are generated by a Python script and pulled in with \includegraphics and \input. The PDF rebuilds itself whenever the data changes. This is the same pattern the class report uses in week 6. → HW 2: the same pattern on the yield curve. task_generate_market_brief writes the charts and tables, and task_compile_market_brief runs latexmk on reports/market_brief.tex. You write one of those tables and the task that compiles the PDF.

  • Which format when. Three formats cover what this course writes:

    • Markdown for documentation, READMEs, and plain technical writing. You have been writing it all along: the text cells of a notebook, the pages of this book.

    • Notebooks, kept as Jupytext .py files, for interactive research and for reports made of charts, tables, and commentary, published as HTML.

    • LaTeX for academic papers, professional PDF reports, heavy math, and anything that needs precise control of the page.

Two live tools to open first:

  • CME FedWatch. You rebuild its market-implied probabilities of the Fed’s policy decisions from fed funds futures.

Databento, in Five Minutes#

  • The chapter: Databento

  • The examples we run: databento/ in the in-class repo

  • The same material as a notebook: Pulling Market Data From Databento

The futures come from Databento, a market data vendor whose CME Globex feed the course subscribes to. Our access is to historical data, not the live stream. It is the pattern you used for WRDS in week 1, with a different kind of credential: an API key in .env, a pull_ function that calls the vendor, and a load_ function that reads what the pull cached. The examples take it in small steps, through the Python client, the raw HTTP API, and a free call that says what a query costs before you run it.

What to take from the demo:

  • What Databento provides, and how to pull historical market data with its Python SDK.

  • How to keep the API key out of the code, in an environment variable read from .env.

  • How a request is specified: a dataset, a schema, and the symbology that names the instrument.

  • How to check what a query costs before you download anything.

Checks and Deliverables#

Both replications are checked against the published numbers. The tests compare your fitted yields with the Fed’s at every maturity from 1 to 30 years, and your FedWatch probability with a recorded reading of the CME tool, and each guide shows how closely they agree.

The pipeline pulls from four sources (CRSP via WRDS, the Fed’s published GSW series, ZQ futures from Databento, and FRED), and the deliverables are a ChartBook site on GitHub Pages and a two-page market brief on the Treasury curve, compiled from LaTeX. We launch it in class; you finish the TODOs and publish on your own.
