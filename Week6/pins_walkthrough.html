Walkthrough: From a Working Folder to a Pin#

This page is the week 6 demo, written down so that you can redo it after class. It uses the class report, the repository you work in for HW 4, and one of its upstreams, ftsfr/fed_yield_curve. Every command runs from a clone of the report, and every block of output is cut down from a real run on November 2. Your hashes and commits will differ where the report or the upstream has moved since.

The words are the ones ChartBook: Pipelines, Stores, and Lineage defines: pipeline, store, snapshot, lockfile, pin, reference, lineage. Read that page first; this one shows each word on the screen.

What you need. About an hour, and:

  • A clone of the report with its environment installed (uv sync in the clone). Activate it once, source .venv/bin/activate, so that the commands below are typed as written; or put uv run in front of each.

  • chartbook --version printing 0.5.0 or newer.

  • A store of your own, holding the snapshots chartbook.lock pins, each built by you (step E shows how, for one of them). chartbook pin --frozen passes when this is set up.

  • jq, for reading the lockfile (brew install jq, or your package manager).

A. The summer edition: a working folder#

What you are about to see: the Summer 2026 edition of the report, on the summer branch. It was built with ChartBook 0.1, which had no snapshots and no pins.

git switch summer
ls chartbook.lock
grep -n -A3 "data.load" src/chart_yield_curve.py
sed -n 140,152p README.md

ls: chartbook.lock: No such file or directory
34:    long = data.load(
35-        pipeline="ftsfr/fed_yield_curve",
36-        dataframe="ftsfr_treas_yield_curve_zero_coupon",
37-        format="pandas",
   chartbook catalog add <the folder where you cloned the ftsfr repositories>/* -y

There is no lockfile. The exhibit reads by name, which is good, but the name resolved through a catalog of working folders on one machine: the README tells you to clone every upstream, run doit in each, and register the folders. Whatever those folders held on the day of the build is what the August PDF shows.

The point: which yield curve did the August report read? Git has the code. Nothing has the data. The folder it read from has been rebuilt since, so August’s bytes are gone, and no one can answer. Do not build summer with ChartBook 0.5 (it needs 0.1.1); switch back.

git switch main

B. The new main: a pin that names its bytes#

What you are about to see: the same exhibit, now reading through a pin. First, where ChartBook will look.

chartbook store info

Store mine: /Users/you/.chartbook/store (writable)
  ftsfr/fed_yield_curve: 1 snapshot(s)
  ... (8 pipelines)
  Newest: 2026-11-02T22:28:14.877522Z

Your own store comes first, because ChartBook writes to the first store in the catalog. The report declares its upstreams in chartbook.toml:

sed -n '/^\[dependencies\]/,$p' chartbook.toml

[dependencies]
"ftsfr/fed_yield_curve" = {}
"ftsfr/ken_french_data_library" = {}
"ftsfr/he_kelly_manela" = {}
"ftsfr/corp_bond_returns" = {}
"ftsfr/options" = {}
"ftsfr/nyu_call_report" = {}

"ftsfr/fed_yield_curve" = {} means: a pipeline named by its ID, found by that ID in a store, with no folder of it on this machine. (chartbook add ftsfr/fed_yield_curve is how such a line gets written: it adds the line and pins the newest snapshot in your stores.) What the report got for it is in chartbook.lock. Two records matter for one dependency: the dependency’s entry, and the record of each asset pinned from it.

jq '.records[0].dependencies[] | select(.id=="ftsfr/fed_yield_curve")' chartbook.lock
jq '.records[] | select(.id=="ftsfr/fed_yield_curve:ftsfr_treas_yield_curve_zero_coupon")' chartbook.lock

  "id": "ftsfr/fed_yield_curve",
  "via": "store",
  "location": { "kind": "store", "commit": "3904ad653ea0bfa8af753ad57f34c6917747fdc0",
                "repository": "https://github.com/ftsfr/fed_yield_curve", ... },
  "snapshot": "2026-11-02T05:22:19.659609Z",
  "pinned_hash": "sha256:aff4ea7deb55d7db86c0bf5852be82496a1dfd743bf9c831960908a7497598d8"

  "id": "ftsfr/fed_yield_curve:ftsfr_treas_yield_curve_zero_coupon",
  "location": { "kind": "file", "path": "./_data/ftsfr_treas_yield_curve_zero_coupon.parquet" },
  "content_hash": "sha256:b63da0404cf9cad95233228f31aa6d0fc19bf8583838cd1ed04032901e5bce2b",
  "size_bytes": 5352937

Four fields to know by name:

Field

Says

commit

Which code built it: the upstream’s commit, 3904ad6

snapshot

When the snapshot was made. This is the snapshot’s name, not when you pinned it; the lockfile records no time of its own

pinned_hash

One hash for the whole dependency: a hash over every asset pinned from it (step C)

content_hash

One hash per file: the SHA-256 of its bytes

Now the walk up from the lockfile:

chartbook lineage

finm-32800/finm_midterm_report (this folder)
├── ftsfr/fed_yield_curve: ftsfr/fed_yield_curve 3904ad6, made 2026-11-02 05:22:19 UTC, pins checked
│   ... (8 lines)
8 snapshot(s) upstream; no gaps.

Each line is a snapshot in a store, checked: it is there, it holds what was pinned from it at those hashes, and its own pins cover its own dependencies. Then read the data, and ask where it came from:

python -c 'from chartbook import data
df = data.load("fed_yield_curve:ftsfr_treas_yield_curve_zero_coupon", format="pandas")
print(df.shape, df.ds.max())
print(data.path("fed_yield_curve:ftsfr_treas_yield_curve_zero_coupon"))'

(382232, 3) 2026-10-02 00:00:00
<store>/pipelines/ftsfr+fed_yield_curve/2026-11-02T052219Z_3904ad653ea0/_data/ftsfr_treas_yield_curve_zero_coupon.parquet

The path is in the store, under the snapshot’s name (its time and commit), and the report’s code never wrote it down: data.load resolved the reference through chartbook.lock. Both spellings of the reference work, fed_yield_curve:... and ftsfr/fed_yield_curve:...; the exhibits use the long one. doit watches that same file:

doit info exhibit:yield_curve

file_dep   :
 - ./src/settings.py
 - <store>/pipelines/ftsfr+fed_yield_curve/2026-11-02T052219Z_3904ad653ea0/_data/ftsfr_treas_yield_curve_zero_coupon.parquet
 - ./src/chart_style.py
 - ./src/exhibits/yield_curve.py

dodo.py builds that list with data.path(...) for every reference in the exhibit’s UPSTREAM. Build it:

uv run doit
doit forget exhibit:yield_curve && doit

.  exhibit:yield_curve
yield_curve: Latest (Oct 2, 2026): 2y 4.80%, 10y 5.28%, 30y 5.66%

A full build from clean takes about a minute; a second doit does nothing. After doit forget, only that exhibit reruns, and nothing after it: the PNG came out byte-identical, and doit compares inputs by hash. Open reports/class_report.pdf at the yield curve page: those are the numbers.

The point: the report names data, never a path. The path comes from the pin, doit watches the pinned file, and the exhibit reruns when, and only when, the pin moves. Data validation would catch bad data; the pin catches different data.

C. The hashes, by hand#

What you are about to see: every hash in the lockfile can be recomputed with shasum and jq. First the file:

shasum -a 256 "$(python -c 'from chartbook import data; print(data.path("fed_yield_curve:ftsfr_treas_yield_curve_zero_coupon"))')"

b63da0404cf9cad95233228f31aa6d0fc19bf8583838cd1ed04032901e5bce2b  <store>/.../ftsfr_treas_yield_curve_zero_coupon.parquet

That is the content_hash from step B. Then the dependency’s hash, which is a hash over a listing, one line per pinned asset, <hex>  <ID>, sorted by ID. Write the listing first, then hash it:

jq -r '.records[]
    | select(.pipeline == "ftsfr/fed_yield_curve" and .content_hash)
    | "\(.content_hash | ltrimstr("sha256:"))  \(.id)"' chartbook.lock \
    | LC_ALL=C sort -k2

47cbb658b68625c2738d0290cf3af12c7fa235933f9c7b1609cf7a52461840f2  ftsfr/fed_yield_curve:chart/yield_curve_replication
b63da0404cf9cad95233228f31aa6d0fc19bf8583838cd1ed04032901e5bce2b  ftsfr/fed_yield_curve:ftsfr_treas_yield_curve_zero_coupon
357c9890e7ba7d62f7a4e4b63f1aa58eba9e3ab1b545085f0edc425a811d1e0a  ftsfr/fed_yield_curve:notebook/gsw_crsp_replication_ipynb
e7510339af9f776c67e151c5f38a487cdb0b731ca50802c6a873352dd1577ec8  ftsfr/fed_yield_curve:notebook/summary_fed_yield_curve_ipynb

Four assets: a chart, the dataframe, two notebooks. Pipe the same listing into shasum, and read the lockfile’s answer next to it:

jq -r '.records[]
    | select(.pipeline == "ftsfr/fed_yield_curve" and .content_hash)
    | "\(.content_hash | ltrimstr("sha256:"))  \(.id)"' chartbook.lock \
    | LC_ALL=C sort -k2 | shasum -a 256
jq -r '.records[0].dependencies[] | select(.id == "ftsfr/fed_yield_curve") | .pinned_hash' chartbook.lock

aff4ea7deb55d7db86c0bf5852be82496a1dfd743bf9c831960908a7497598d8  -
sha256:aff4ea7deb55d7db86c0bf5852be82496a1dfd743bf9c831960908a7497598d8

The same hash. (The recipe matches for all eight dependencies in the report’s lockfile.) Change one byte of one file upstream and the file’s content_hash changes, so the listing changes, so the pinned_hash changes: one line of a diff says something moved.

Now git, for contrast. A commit is a hash over its tree and its parent; a tree is a hash over the names and hashes of what is inside it.

git cat-file -p HEAD
git cat-file -p 'HEAD^{tree}' | head -12
git rev-parse HEAD:chartbook.lock
printf 'blob %s\0' $(wc -c < chartbook.lock | tr -d ' ') | cat - chartbook.lock | shasum -a 1

parent d3bea64dcfe3e0fd1cdae165d4e2e9c676f7ca36

...
100644 blob 0fd4837aa8f0f4990fafbc08ae9bebcb467232c4	chartbook.lock

The last two lines are git’s hash of chartbook.lock and the same hash made by hand: SHA-1 of blob <size>\0 followed by the file. The lockfile’s own hash sits in the tree, the tree’s in the commit, the commit’s in its child.

The point: git’s one commit hash covers every file and all of history, a full Merkle tree. ChartBook stops a level short: a pinned_hash covers one dependency’s files, and a snapshot is named by its time and commit, not by a root hash. chartbook lineage checks the graph edge by edge instead. (chartbook lineage --rehash also reads every byte again; in ChartBook 0.5.0 it reports every object as a gap when more than one store is registered, so until a release fixes that, run it with one store named: CHARTBOOK_STORE="<the store's path>" chartbook lineage --rehash. chartbook store verify rehashes a store and is not affected.)

D. A live git dependency#

What you are about to see: a public branch that grows by a row a day becomes a pinned upstream, with no snapshot made by its owner. The example is the Yield Spread Monitor from week 5, whose monitor-history branch holds spread_history.csv. For HW 4, your version of this step is your own HW 3 monitor; Make Your Homework an Upstream on the HW 4 page has the exact files for it.

In class, the instructor added three files to that branch, through GitHub’s web interface (switch to monitor-history, then Add file, committing to that branch and not a new one). The daily workflow writes only spread_history.csv there, so the files stay. chartbook.toml:

Sixteen more bytes: one row. The point: a pin never moves by itself. When it moves, the lockfile diff says what moved, and that diff is what you commit and what your reviewers read.

One thing to know about ChartBook 0.5.0: a classmate who clones your branch and runs chartbook pin sees 1 put back in the store, after which pin --frozen and data.load say the store does not have the pinned bytes; chartbook update yield_spread_monitor puts them right, and if the branch has moved since you pinned, git diff chartbook.lock shows it and git restore chartbook.lock undoes it. A later release restores a git dependency’s files correctly, and this step goes away.

E. Rebuild versus read#

What you are about to see: the same code, run at a later point in time, gives a different hash, and the hash tells you so. Step B read a snapshot from a store. Now build the upstream yourself, at the commit the lockfile names. In a second terminal, so that the report’s environment stays active in the first:

git clone https://github.com/ftsfr/fed_yield_curve
cd fed_yield_curve
git switch --detach 3904ad6
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt "pyarrow==20.0.0" jupytext
chartbook trust
chartbook run --snapshot

(3904ad6 is the commit from step B; read it from the lockfile with jq -r '.records[0].dependencies[] | select(.id=="ftsfr/fed_yield_curve") | .location.commit' chartbook.lock in the report. The two extra packages: the pipeline’s requirements.txt pins numpy==1.26.4, which the newest pyarrow refuses, and its notebooks need jupytext; pyarrow==20.0.0 is also what wrote the pinned file, which matters at the end of this step.) chartbook trust says this folder’s build script may run on your machine. chartbook run --snapshot checks that everything is committed, builds (about a minute: it pulls the Fed’s yield curve file, formats it, runs the tests and two notebooks, and draws the chart), and copies what it built into your store:

ftsfr/fed_yield_curve: build
...
ftsfr/fed_yield_curve at 3904ad6: 4 asset(s) in the store
Snapshot made. A pipeline that depends on this one gets it with `chartbook update`.
Stores: mine

Compare what you built with what the report pinned:

shasum -a 256 _data/ftsfr_treas_yield_curve_zero_coupon.parquet

bc106bbafd76e3ac33ee0b60bc0c8a1ccf96b09153d0773529853427766ec005  _data/ftsfr_treas_yield_curve_zero_coupon.parquet

Pinned b63da040..., rebuilt bc106bba.... Same commit, different bytes. The rebuild runs through October 23 (382,652 rows); the pin ends October 2 (382,232 rows). The rows they share agree exactly: the Fed published three more weeks and revised nothing. Back in the report, ChartBook sees the newer snapshot in your store and says so, without moving anything:

chartbook pin | grep -A5 fed_yield

ftsfr/fed_yield_curve: 4 changed upstream since it was pinned
  changed upstream: ftsfr/fed_yield_curve:ftsfr_treas_yield_curve_zero_coupon
  ... (chart, two notebooks)
4 pinned asset(s) have changed upstream. `chartbook update` moves the pins.

Do not commit this in the shared report: the snapshot exists in your store only, so every classmate’s build, your reviewers’ included, would fail at chartbook pin --frozen. The HW 4 rule is that the pins in chartbook.lock are shared; if your exhibit needs the newer data, run chartbook update <name> and say so in your pull request, where the lockfile diff shows what moved.

Finally, does the rebuild reproduce the pin if you cut it at the pinned date? Save this as trim_and_hash.py and run it in the clone, with the clone’s environment:

"""Cut a rebuilt yield-curve file at the pinned date and hash what remains."""
import hashlib
import sys
from pathlib import Path

import pandas as pd
import pyarrow

src = Path(sys.argv[1])            # the rebuilt file
cutoff = sys.argv[2]               # the last date the pin holds
out = Path("trimmed.parquet")

df = pd.read_parquet(src)
df = df[df["ds"] <= cutoff]        # keep the index: the pipeline wrote it
df.to_parquet(out)
digest = hashlib.sha256(out.read_bytes()).hexdigest()
print(f"rows {len(df):,}, through {df['ds'].max():%Y-%m-%d}, "
      f"pyarrow {pyarrow.__version__}, pandas {pd.__version__}")
print(f"sha256:{digest}")

Byte for byte the pin. The same rows written by pyarrow 26.0.0 hash to 62a8f97f5b01..., and by pyarrow 26.0.0 with pandas 3.1.0 to 5bb9af54f6d1...: same rows, three writers, three hashes.

The point: the hash pins the bytes, not the numbers. A rebuild reproduces a pin only with the same code, the same inputs, and the same environment, which is what uv.lock is for. When the hashes differ, the snapshot’s record says which commit made it and when, and that is where you start looking.

F. When do pins move#

Command

Pins

chartbook add <ID>, chartbook pin

Create a pin for a dependency that has none. Never move one; say changed upstream when a newer snapshot exists

chartbook run (and uv run doit in the report)

Never move one. The build reads the pinned snapshot. run also pins what has no pin yet, and builds a git dependency once

chartbook update [<name>]

Move: to the newest snapshot, or to what a branch means now. The lockfile diff is the record; commit it on its own

chartbook pin --frozen, chartbook run --frozen

Write nothing. Refuse if any pin is missing or not in a store. What CI runs

A git dependency with rev = "<commit>"

Cannot move: update fetches again and the commit means the same thing. A tag likewise; a branch moves

chartbook store gc

Keeps every snapshot a lockfile pins, the newest of each pipeline, and anything from the last seven days; removes the rest, after asking

For HW 4: chartbook pin after you add a line to [dependencies], read the diff, commit chartbook.lock, and leave the other pins where they are.
